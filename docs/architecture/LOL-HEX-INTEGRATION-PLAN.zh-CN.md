# LOL Hex 内置化改造方案

> 状态：方案阶段，尚未开始功能代码改造  
> 目标分支：`feature/hex-integration`  
> 基线分支：`dev`  
> 基线提交：`f9bd2e6d3e034b2ce5ca0b79a8ea6f1ec2968e26`

## 1. 改造目标

将 LOL Hex 从“扩展管理”中的独立扩展，调整为 My-LiveHub 正式内置功能。用户安装或解压 My-LiveHub 后即可获得 Hex 的完整功能，不再需要单独理解扩展目录、单独部署 Python 环境或手动维护 Hex 发布文件。

本次内置化首先统一产品入口、安装包内容、资源版本和更新生命周期；不以“把所有 Python 代码改写为 Go”作为前置条件。

## 2. 当前实现与判断

当前实现已经具备部分主程序集成能力：

- Go 层存在 `LOLHexService` 和 `LOLHexModule`，由模块管理器启动、停止和查询状态。
- 主程序场景服务已经识别 `lol_hex_display` 与 `lol_hex_bar` 图层类型。
- 前端存在独立的扩展管理页面，并通过主程序模块 API 管理 Hex 进程。
- Hex 有自己的管理页、海克斯展示页和战绩条页面，默认本地端口为 8767。
- 主程序托管模式下由主程序统一负责 OBS WebSocket 连接，Hex 继续负责游戏客户端识别、截图、OCR、海克斯数据和自身页面。

尚未完成的部分：

- 产品入口仍然把它呈现为“扩展”，而不是正式功能。
- 业务运行时仍是独立 Python/Flask 进程，源码运行依赖 Python 环境，发布运行依赖独立打包的目录式 EXE。
- Hex 发布目录需要额外放入主程序发布目录；主程序更新器目前按 Portable ZIP 或 Setup EXE 更新整套应用，没有独立的 Hex 组件版本协议。
- Hex 的本机配置、数据、截图和日志需要在升级及迁移时明确保护。
- Windows F1 全局热键存在管理员权限要求。当前通过独立进程处理权限边界；不能简单把提权转移到整个主程序。

## 3. 总体架构决策

**产品层面内置，运行层面先保留独立进程。**

目标形态：

1. My-LiveHub 将 Hex 作为正式内置模块展示和管理，不再让用户进入“扩展管理”寻找它。
2. Hex 的运行文件、Python 运行时（若继续采用 Python）、OCR 模型及必要静态资源随 My-LiveHub 安装包/Portable ZIP 一起发布。
3. Go 主程序继续管理 Hex 的生命周期、状态、日志入口和版本信息。
4. Hex 的 OCR、截图、LCU 轮询和 F1 全局热键继续在独立进程运行，避免阻塞主程序，也避免因热键权限要求而让整个 My-LiveHub 都以管理员身份运行。
5. 主程序更新器负责将同一版本发布中的 Hex 运行文件一并更新；用户数据目录不随程序文件覆盖。

暂不采用“立即将 Python 全部重写为 Go”的方案。OCR/ONNX、截图采集、键盘钩子及现有业务逻辑已经有可用实现，整体重写会显著扩大回归范围。

## 4. 用户侧目标体验

- 主界面提供明确的“LOL Hex / 海克斯助手”正式功能入口。
- 不再把 Hex 描述为可选第三方扩展。
- 首次启动时检查内置运行文件和资源是否完整；缺失时给出明确、可操作的错误，而不是要求用户自行猜测 Python 环境。
- Hex 的启动、停止、运行状态、管理页、海克斯展示页和战绩条入口仍可用。
- 是否随 My-LiveHub 启动应由正式功能设置控制；初始默认行为沿用当前“不自动启动”，避免升级后突然启动游戏监控进程。
- 已有场景中的 Hex 图层保持原样，不要求用户重新创建或重新摆放。

## 5. 改造范围

### 5.1 产品入口与模块管理

重点检查并调整：

- `app/frontend/src/views/ExtensionsView.vue`：移除 Hex 专属卡片，不再把 Hex 作为普通扩展管理。
- 当前主导航、路由和设置页面：增加正式功能入口，入口名称和交互与其他内置功能一致。
- `app/internal/desktop/lol_hex_module.go`：保留模块生命周期能力，补齐正式模块的启停策略和错误呈现。
- `app/internal/desktop/lol_hex_service.go`：保留进程身份令牌、外部进程不接管、只停止本程序拥有进程等安全行为；完善资源定位和健康检查。

不应在本阶段顺手重构无关模块管理逻辑。

### 5.2 运行文件与资源打包

目标是让正式发布产物天然包含 Hex，不再要求用户单独执行扩展的 `build.bat` 或手动复制 `dist/lol_hex_display`。

需要逐项核对并修改：

- Windows 安装版打包配置及 Portable ZIP 组装脚本。
- Hex 的目录式 EXE、依赖 DLL、OCR 模型、模板、静态文件和页面模板是否完整进入发布产物。
- 开发模式继续允许使用源码与本地 Python 环境；发布模式必须优先使用随应用发布的运行文件。
- 资源路径必须基于应用安装根目录解析，不能依赖当前工作目录。
- 打包产物中不得包含 `.venv`、缓存、日志、截图、PID 文件和本机配置。

需要先审查现有 Windows 打包脚本与 CI workflow，再确定具体改动点；本方案不授权运行安装包/Portable ZIP 打包 workflow。

### 5.3 配置与用户数据迁移

程序文件与用户数据必须分离。

建议目录边界：

- 程序只读资源：随版本发布，放在应用安装目录的内置 Hex 资源目录。
- 用户配置：继续使用 My-LiveHub 的 `config/local` 管理，不将机器路径写入默认模板。
- 持久化业务数据：放入 My-LiveHub 的用户数据根目录下独立的 Hex 数据子目录。
- 截图、日志：放入用户数据目录，不放在可能被更新器替换的程序资源目录。
- 临时文件、PID：放在 Hex 运行时目录或系统临时目录，并在退出后清理。

迁移必须兼容当前路径和配置：

- `config/default/lol_hex_display.json`
- `config/local/lol_hex_display.json`
- 旧扩展目录下的 `config.txt` 兼容迁移逻辑
- 旧的 `data/`、`screenshots/`、`logs/` 与已有卡片、索引、截图

迁移原则：

1. 首次启动检测旧路径。
2. 先复制到新目录并校验文件数量/大小或关键索引可读性。
3. 新配置写入成功后才标记迁移完成。
4. 不自动删除旧目录；保留回滚窗口。
5. 已存在的新配置优先，不覆盖用户当前设置。
6. 截图、卡片、索引和用户自定义内容不得因升级丢失。

具体数据目录应复用项目现有用户数据目录规范，不另起一套不兼容的路径体系。

### 5.4 更新器与版本管理

当前更新器从 GitHub Release 下载完整 Portable ZIP 或 Setup EXE，并在应用目录执行替换。内置化后 Hex 的程序资源应随这两个完整发布包同步更新。

第一阶段不引入独立 Hex 在线更新器，也不让 Hex 自行下载可执行文件。

建议：

- 主程序版本作为整包版本；每个 Release 的 Hex 资源与主程序版本绑定。
- 增加 Hex 内部组件版本/构建标识，供诊断和完整性检查使用，不作为独立更新通道。
- 更新替换范围只包含程序文件和内置资源；用户配置、数据、截图、日志必须排除。
- 更新后执行轻量资源完整性检查；检查失败时明确提示并保留日志，不要静默启动半套 Hex。
- 兼容旧版用户目录和旧扩展目录，不能因目录迁移而让旧版本升级链路中断。

必须分别验证 ZIP 免安装版和安装版 EXE。当前更新器已经有完整包下载、SHA256 校验和独立替换流程，本次改造应尽量复用，不改变已稳定的更新机制。

### 5.5 页面与接口整合

短期保留 Hex 自身 HTTP 服务和页面，避免一次性重写全部前端：

- 管理页、展示页、战绩条地址先保持兼容。
- 主程序统一提供正式入口和状态管理。
- 主程序场景图层继续使用现有 `lol_hex_display`、`lol_hex_bar` 类型。
- 后续再评估将 Hex 页面静态资源托管到主程序浏览器源服务、将 API 合并到主程序服务的收益。

接口整合必须保持现有 OBS 浏览器源 URL 和用户已保存场景的兼容性；如确需变更，必须提供旧 URL 兼容层。

### 5.6 权限与安全

- 不得为了 F1 热键让整个 My-LiveHub 默认以管理员身份运行。
- 保留 Hex 进程单独提权/权限处理能力，先验证当前 UAC 启动链路在内置资源目录下仍有效。
- 保留随机 manager token 和 PID 身份核验。
- 不允许停止用户独立启动的外部 Hex 进程。
- 本地 HTTP 服务只监听回环地址，不能无意暴露到局域网。
- 资源完整性检查不能执行未经校验的外部下载内容。

## 6. 分阶段实施

### 阶段 0：基线与发布链路摸底

- 记录当前 dev 上 Hex 的运行、配置、页面、场景和更新行为。
- 完整梳理 Windows 安装包与 Portable ZIP 的文件收集规则。
- 梳理用户数据目录、配置管理器和旧路径。
- 建立 Hex 当前核心功能回归清单。
- 不改业务逻辑，不改变用户现有行为。

交付：打包/更新/数据路径清单和可重复的基线测试结果。

### 阶段 1：正式内置入口

- 从“扩展管理”移出 Hex 专属管理卡片。
- 在正式功能导航中提供 Hex 入口。
- 复用现有 Go 服务和模块生命周期。
- 保持启动默认关闭、原有场景图层和页面入口兼容。

交付：源码开发环境可正常启停和使用，旧扩展入口不再是唯一入口。

### 阶段 2：运行资源随包发布

- 将 Hex 发布文件纳入安装版和 Portable ZIP 的统一文件清单。
- 建立开发/发布两种运行资源定位规则。
- 发布模式不依赖用户机器全局 Python 安装。
- 资源缺失时给出明确诊断。

交付：干净 Windows 环境安装后，无需用户手工安装 Python 或复制 Hex 文件即可启动 Hex。

### 阶段 3：数据目录与旧版迁移

- 明确程序资源目录和用户数据目录。
- 实现可重复、可恢复的旧目录迁移。
- 对配置、截图、卡片、索引、日志进行保护。
- 验证升级中断后再次启动不会重复破坏数据。

交付：旧版升级后设置和用户数据完整，旧目录保留至确认迁移成功。

### 阶段 4：更新器联动与发布验证

- 确认整包更新会同步更新 Hex 资源。
- 确认更新不会覆盖用户数据。
- 检查版本标识和资源完整性。
- 分别验证 Portable ZIP 与安装版 EXE 的更新链路。

交付：两种发行形态升级后 Hex 版本与主程序匹配，且数据不丢失。

### 阶段 5：服务边界优化（非本轮前置）

- 评估 Hex 页面是否迁入主程序静态资源服务。
- 评估 API 是否统一到主程序 HTTP 服务。
- 仅迁移低风险、无权限依赖的业务逻辑。
- OCR、截图和全局热键仍可独立进程运行。

该阶段单独评估收益，不与前四阶段捆绑，避免把内置化变成大规模重写。

## 7. 回归测试与验收标准

### 功能回归

- LCU 客户端未启动、启动中、已登录、退出等状态识别正确。
- F1 截图采集、框选、Esc 取消和重复触发行为正常。
- OCR 正常识别；低置信度时保留截图供人工确认，不生成猜测结果。
- 海克斯索引检查/更新/重建正常。
- 海克斯展示页和战绩条正常。
- OBS 综合展示中原有 Hex 图层不丢失、不变形，布局无需重建。
- 主程序关闭时只停止本程序拥有的 Hex 进程；外部进程不被误杀。
- UAC 取消、启动失败、Hex 崩溃和端口占用均有明确状态及错误提示。

### 发布与升级回归

- Windows 干净环境安装版首次启动。
- Windows 干净环境 Portable ZIP 首次启动。
- 机器没有全局 Python 时仍可启动发布版 Hex。
- ZIP 免安装版升级后 Hex 文件已更新，用户数据保留。
- 安装版升级后 Hex 文件已更新，用户数据保留。
- 旧扩展目录升级迁移后，配置、截图、卡片和索引均可用。
- 更新中断/资源缺失时能够诊断和恢复。

### 验收底线

以下任一项未通过，不得合并到 master：

1. 两种发行版都能在无额外 Python 配置的干净 Windows 环境启动 Hex。
2. 用户原有 Hex 配置、截图、卡片、索引及场景布局没有丢失。
3. 主程序更新能同步更新 Hex，且不会覆盖用户数据。
4. F1/UAC 权限边界正确，不要求整个主程序长期以管理员运行。
5. 原有 Hex 识别和展示功能无回归。

## 8. 明确不做的事

- 不在 master 直接开发。
- 不把本次 Hex 改造拆到 dev 或其他临时分支。
- 不创建额外临时分支或 PR。
- 不立即把现有规模较大的 Python 业务逻辑整体重写为 Go。
- 不擅自删除旧扩展目录或用户数据。
- 未经明确要求不运行 Windows 安装包/Portable ZIP 打包 workflow。
- 不改变现有更新器已验证稳定的下载、校验和替换机制，除非测试证明必须修改。

## 9. 分支与后续工作约定

- 所有 Hex 相关代码、测试、资源打包和文档改动统一提交到 `feature/hex-integration`。
- 该分支以当前 `dev` 的 `f9bd2e6d3e034b2ce5ca0b79a8ea6f1ec2968e26` 为起点。
- 不直接修改 `dev` 或 `master`；其他非 Hex 工作仍按原有流程在 dev 处理。
- 若 dev 后续出现与 Hex 改造相关的必要修复，先在本分支明确同步策略并检查冲突，不盲目覆盖。
- 每个阶段独立测试并提交，提交信息明确标注 Hex。
- 所有阶段验收完成后，再由用户决定是否将该分支合并回 dev；之后仍需按正常流程验证后才考虑进入 master。
