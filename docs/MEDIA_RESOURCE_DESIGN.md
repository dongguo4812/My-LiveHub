# 多平台媒体资源管理专项设计

> 文档版本：V0.1（设计稿）
> 状态：方向已确认，接口细节待实现前评审
> 更新日期：2026-11-09
> 适用范围：弹幕表情、礼物图片，以及后续可复用的直播媒体资源

## 1. 设计目标

为 My-LiveHub 建立与直播平台无关的媒体资源管理能力。B 站、抖音及后续平台可以使用各自不同的接口、协议和资源格式获取表情与礼物，但核心层只处理统一资源模型和统一缓存服务。

本设计需要满足：

1. 新增平台时，不复制一套表情/礼物缓存代码。
2. 平台资源获取方式可以不同，不要求所有平台都提供完整资源列表接口。
3. 支持主动获取资源目录和收到事件后被动发现资源两种方式。
4. 资源目录、图片文件缓存、实时事件三者分离。
5. 模拟事件能够选择当前平台已登记的真实资源，并进入与真实事件相同的处理链路。
6. 资源查询、目录刷新、图片下载和磁盘操作不得阻塞直播连接、事件接收、事件分发或窗口渲染。
7. 本地资源目录和图片缓存不提交 Git，也不进入正式发布包。

## 2. 核心概念与边界

### 2.1 媒体资源（Media Resource）

媒体资源是平台侧某个表情或礼物的描述信息，例如资源 ID、名称、图片 URL、尺寸等。资源记录不等于图片文件本身。

### 2.2 资源目录（Resource Catalog）

资源目录是某个平台、某个来源范围内已知媒体资源的集合。来源范围可以是平台全局、账号、直播间或频道，具体由平台适配器声明。

- 平台提供列表接口：适配器主动获取并更新目录。
- 平台不提供完整列表：从实际收到的弹幕/礼物事件中逐步发现并登记。
- 列表接口暂时不可用：保留上次成功目录，并标记刷新状态；不得阻止直播连接。
- 资源目录按需刷新，不在程序启动时无条件扫描所有平台或下载全部图片。

### 2.3 图片缓存（Image Cache）

图片缓存只负责将经过平台安全策略验证的图片 URL 异步下载到本地，并提供本地访问地址。它不负责判断图片属于哪个平台、哪个礼物或哪条弹幕。

### 2.4 事件（Event）

实时事件携带平台标识、资源类型、可用的平台资源 ID、名称及原始图片 URL。事件不依赖缓存是否已完成；缓存未命中时继续使用原始 URL。

## 3. 统一资源模型

建议核心层定义如下概念模型，字段类型可在实现前结合现有事件模型统一：

| 字段 | 含义 |
|---|---|
| platform_id | 平台标识，如 bilibili、douyin |
| source_id | 资源所属来源范围，如直播间/频道 ID；平台全局资源可为空 |
| resource_type | 资源类型，首期为 emoticon、gift |
| resource_id | 平台原生资源 ID；平台没有 ID 时允许为空 |
| name | 资源名称或表情文本 |
| image_url | 平台提供的原始图片 URL |
| width / height | 图片显示尺寸，可选 |
| metadata | 平台特有的补充信息，不强行映射成所有平台共有字段 |
| first_seen_at / updated_at | 首次发现及最近更新时间 |

### 3.1 资源身份与图片文件身份必须分开

资源记录的逻辑身份建议为：

platform_id + source_id + resource_type + resource_id

如果平台没有稳定资源 ID，则使用平台、来源范围、资源类型及规范化后的图片 URL 作为备用身份。

图片文件缓存则以规范化图片 URL 的 SHA-256 作为内容地址。这样：
- 不同平台即使资源 ID 相同，也不会发生资源记录冲突。
- 同一图片 URL 被多个资源引用时，可以复用同一份图片文件。
- 图片 URL 更新时，资源记录可以更新指向，而不会把旧图片误认为新图片。
- 不能仅使用礼物 ID 作为图片缓存文件名。

## 4. 平台适配器职责与接口方向

平台适配器负责平台差异，不负责实现自己的图片下载队列或本地缓存。

建议逐步为平台适配器增加可选的媒体资源能力接口，避免把媒体资源方法强制加入所有基础连接接口：

- 查询/刷新资源目录：支持时返回指定来源范围内的资源列表。
- 查询已知资源：按资源类型、来源范围和关键字分页查询。
- 从事件发现资源：平台事件转换时提取礼物/表情信息并交给核心登记。
- 提供图片 URL 安全策略：声明允许访问的 HTTPS 域名或平台认可的资源来源。
- 报告能力状态：区分 supported、unsupported、unavailable，并提供原因。

能力接口是可选能力。某个平台不支持完整目录接口，不代表它不能使用统一缓存；它仍可通过事件携带的 URL 被动发现资源。

适配器不得把平台 Cookie、签名参数或鉴权细节暴露给前端。若图片地址必须依赖鉴权才能获取，应由平台适配器提供受控资源获取方式，不能把敏感凭据拼进公共资源记录。

## 5. 统一媒体资源管理器

核心层的媒体资源管理器负责：

1. 接收平台适配器提交的资源目录和事件中发现的资源。
2. 标准化资源字段并按资源身份去重、更新。
3. 按平台、来源范围和资源类型查询资源目录。
4. 将资源的原始图片 URL 交给统一图片缓存服务。
5. 向事件展示层返回原始 URL 和可用的本地缓存 URL。
6. 为模拟器提供当前平台的资源列表。
7. 记录资源目录的获取时间、刷新状态及错误原因。

管理器不直接发起平台网络请求；平台 API 调用由对应适配器完成。资源目录刷新由后台任务执行，采用超时、取消和有限重试，不影响平台连接与事件处理。

## 6. 统一图片缓存服务

### 6.1 处理流程

1. 收到资源或事件中的原始图片 URL。
2. 通过平台对应的 URL 安全策略进行快速校验。
3. 查询本地缓存；命中则立即返回本地 URL。
4. 未命中则立即返回原始 URL，同时向有界后台队列提交下载任务。
5. 下载完成后原子写入本地缓存；后续同一图片资源命中本地缓存。
6. 下载失败不改变原始 URL 的展示逻辑，并按退避策略允许后续重试。

缓存未完成期间不得等待网络或磁盘操作。相同 URL 的并发下载必须合并；队列必须有界，队列满时非阻塞放弃本次预取，后续资源再次出现时可以重新调度。

### 6.2 图片加载回退

展示层统一采用以下优先级：

1. 本地缓存图片可用：显示本地图片。
2. 本地图片加载失败：回退原始平台图片 URL。
3. 原始图片也加载失败：回退表情文字或礼物名称/默认内容。

下载成功不要求强制替换当前正在显示的事件；后续同一资源再次出现时优先使用本地缓存。

### 6.3 跨平台 URL 安全

当前实现的下载域名白名单只覆盖 B 站，不能直接作为多平台最终方案。统一缓存服务必须采用按平台注册的 URL 安全策略：

- 每个平台适配器声明可信 HTTPS 图片域名或受控资源来源。
- 初始 URL 和每一次 HTTP 重定向都必须重新校验。
- 禁止访问 localhost、内网、链路本地、保留地址及其他非公网目标，防止 SSRF。
- 下载任务在后台执行 DNS/目标地址安全检查；事件接收路径不做网络探测。
- 限制响应大小、超时、重定向次数及并发数。
- 只接受有效图片响应；文件写入采用临时文件和原子替换。
- 不允许为了兼容某个平台而关闭全局安全校验。

平台若使用动态 CDN 域名，应由适配器提供可维护的域名策略；不能简单地允许任意 HTTPS URL。

### 6.4 本地存储

- 图片文件保存在用户数据目录的缓存区域，不放在源码目录。
- 资源目录元数据与图片二进制文件分开管理。
- 元数据具体采用 SQLite 还是轻量文件存储，沿用项目整体存储方案评估，不在本专项中提前强制决定。
- 缓存可重建；清理缓存文件不应破坏真实事件记录。
- 本地缓存目录加入 Git 忽略规则，不提交仓库，不打包进正式发布产物。

## 7. 资源目录获取与生命周期

### 7.1 连接时

平台连接流程只负责尽快建立直播连接。资源目录刷新作为独立后台任务启动：
- 不等待资源列表 API 返回。
- 不因目录接口失败而判定直播连接失败。
- 有上次成功目录时继续使用旧目录。
- 首次获取失败时允许模拟器显示“尚未获取到该平台资源”，但不伪造礼物或表情。

### 7.2 运行期间

- 收到新礼物/表情事件时，若资源尚未登记，则被动登记。
- 发现同一资源图片 URL 变化时更新资源记录。
- 刷新任务合并，避免同一来源范围重复并发刷新。
- 平台断开后取消与该连接生命周期绑定的任务；已完成的本地缓存保留。

### 7.3 目录范围

资源查询必须带平台标识，并在适用时带来源范围。不能把某个直播间专属礼物误显示到另一个直播间，也不能因为两个平台资源 ID 相同而混淆。

## 8. 统一事件与展示字段

标准事件中媒体字段建议采用可选结构，而不是为每个平台不断增加专属字段：

- 礼物资源：resource_type、resource_id、name、image_url。
- 表情资源：文本 token 与对应媒体资源信息；一条弹幕可包含多个表情。
- 展示层缓存地址由核心媒体资源服务补充，属于本地运行时字段，不作为平台原始事件数据。

平台原生数据仍保留在 raw_data 或平台扩展字段中，以便未来补充平台独有展示能力。不能为了统一而丢失平台特有信息。

## 9. 模拟器资源选择

模拟器平台选择与资源选择联动：

1. 选择平台后，查询该平台当前可用的资源目录。
2. 选择事件类型为礼物时，只列出该平台已登记的礼物资源。
3. 选择弹幕表情时，使用该平台已登记的表情资源；必要时支持把选中的表情插入模拟弹幕内容。
4. 生成模拟事件时携带 platform_id、resource_id、resource_type、name、image_url，并标记 is_simulated=true。
5. 模拟事件进入与真实事件相同的媒体资源登记、缓存和展示流程。
6. 目录为空时明确显示尚未获取/暂不支持目录/尚未发现资源等状态，不提供虚构数据。
7. 模拟事件不得触发真实平台发送、真实统计或其他未授权外部副作用。

模拟器不自行请求 B 站或抖音接口，也不单独维护一套礼物列表。

## 10. 建议接口分层（概念示意）

~~~text
platform.Adapter
  ├── Connect / Disconnect
  └── 可选 MediaCatalogProvider
        ├── RefreshCatalog(source, resourceType)
        ├── ListResources(source, resourceType, filter)
        └── URLPolicy()

media.ResourceManager
  ├── Register / Update
  ├── Find / List
  ├── RefreshAsync
  └── ResolveImage

media.ImageCache
  ├── CachedURL
  ├── Prefetch
  └── ServeHTTP

simulator
  └── 通过 ResourceManager 查询平台资源
~~~

以上为职责边界示意，不是要求立即按图创建所有包或接口。实现时应优先复用现有 platform、events、media 目录，避免为了抽象而过早拆分。

## 11. 当前实现迁移计划

### 第一步：抽象当前 B 站实现

- 保留现有 B 站礼物目录获取和弹幕表情解析能力。
- 将 B 站资源转换为统一媒体资源记录。
- 把 B 站图片域名校验从通用缓存逻辑中分离，改为 B 站 URL 策略。
- 统一缓存服务不再内置 B 站专属域名判断。
- 目录刷新改为后台异步任务，不阻塞直播连接。
- 保持当前“原始 URL 即时回退、本地缓存后台下载”的显示行为不变。

### 第二步：接入模拟器

- 增加按平台、事件类型查询资源目录的接口。
- 礼物模拟器从统一资源管理器选择礼物。
- 模拟事件完整携带资源 ID、名称和图片 URL。
- 使用同一缓存服务验证命中、下载、失败回退。

### 第三步：第二个平台验证

- 接入第二个平台的媒体资源提供能力。
- 验证平台资源 ID 隔离、来源范围隔离、不同 CDN 白名单、目录缺失时的被动发现。
- 验证模拟器不依赖平台专属代码。
- 验证一个平台目录接口失败不会影响其他平台和核心事件链路。

## 12. 性能与验收要求

- 直播连接不等待礼物/表情目录接口。
- 弹幕和礼物事件处理不等待图片网络下载或磁盘写入。
- 缓存查询仅进行有界本地操作；下载任务异步、有界、去重。
- 一个平台资源接口超时或失败，不影响其他平台连接和事件。
- 多平台同 ID 资源不串数据；相同图片 URL 可安全复用文件缓存。
- 缓存文件缺失或损坏时可以重新下载，展示始终保留原始 URL 回退。
- 模拟器选择的资源与实际平台目录一致。
- 本地缓存不进入 Git 和正式发布包。
- 增加单元测试覆盖资源身份、平台隔离、URL 安全策略、目录刷新并发、缓存回退及模拟事件字段。
- 性能验证关注事件路径新增耗时，不能引入同步 HTTP 请求或等待后台任务。

---

**设计结论：** 平台适配器负责发现和描述平台媒体资源；核心媒体资源管理器负责标准化、目录查询与资源身份；统一图片缓存服务负责安全、异步地保存图片；事件展示与模拟器只消费统一资源模型。新增平台时只需实现平台资源提供能力，不需要复制缓存和展示逻辑。
